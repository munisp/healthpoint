# Theoretical throughput ceilings — vendor-claimed, NOT measurements

**Every figure below is a vendor-published design point, marketing number, or
third-party benchmark — none were measured on this platform.** No TPS numbers
exist for the HealthPoint IDR stack until `loadtest/k6-*.js` is executed
against a deployed environment (see README). Use these only to sanity-check
measured results (e.g. if a measurement exceeds a ceiling, distrust the
measurement).

| Component | Vendor-claimed ceiling | Source |
| --------- | ---------------------- | ------ |
| **TigerBeetle** (ledger) | ~1,000,000+ transfers/sec *client-side batched submission* (Zig client: 1,563,167 t/s; Go: 1,471,084 t/s; Java: 1,273,476 t/s; C#: 1,521,359 t/s — 1M-transfer batch submission benchmarks, 7–9 ms max batch latency). This is the design point enabled by batching up to ~8,190 operations per 1 MB message. **Independent end-to-end numbers are far lower**: a third-party benchmark measured ~46,600 transfers/sec single-worker on an M4 Mac Mini (0.16.x), and SoftwareMill measured ~42k TPS vs ~15k TPS for a batched Postgres approach. | TigerBeetle blog, "Writing High-Performance Clients for TigerBeetle" (via theartofcto.com summary, 2026-01); backend.how "1B Payments/Day" benchmark (2026-05); SoftwareMill benchmark (via theartofcto.com) |
| **Kafka** (event backbone) | "Millions of messages per second" on a properly-sized multi-broker cluster (vendor/marketing literature; a commonly-cited figure is ~2M msg/s on a standard cluster). Per-broker practical ceilings are workload-dependent (message size, acks, replication factor). This compose stack runs a **single broker**, so the real ceiling here is one broker's disk/network, not the cluster figure. | Confluent/Apache Kafka marketing and benchmark literature (softwarelogic.co Kafka overview); single-broker caveat is intrinsic to docker-compose.yml (one broker, RF=1) |
| **PostgreSQL 16** (OLTP) | No single vendor ceiling; pgbench (TPC-B-like) results are hardware-bound. Reference points: ~900 TPS in the official docs' trivial example (10 clients, 1 thread); ~2,400 TPS on a 2-core laptop; ~19k TPS mixed / ~23k TPS write-heavy / ~287k TPS read-only on NVMe-optimized storage with 256 clients. **Expect low-thousands TPS for write workloads on this compose stack** (single container, default config, one disk). | postgresql.org pgbench docs (typical output ~897 TPS); community pgbench run (~2,440 TPS, 2-core i5); simplyblock benchmark report (2025-06, up to 19k TPS mixed) |
| **ml-service** (FastAPI + PyTorch CPU inference) | No vendor ceiling exists — single-process uvicorn, CPU torch. Must be measured with `k6-disputes.js` (endpoint tag `ml.fraud.score`). | n/a — measure |
| **APISIX / Caddy edge** | Not the expected bottleneck for these workloads; measure if saturation appears before app-tier saturation. | n/a — measure |

## How to use this table

1. Run the k6 scripts; record per-endpoint throughput and p95/p99 (README).
2. Identify the saturating component (Postgres locks/connections, Kafka lag,
   ml-service CPU, ledger client).
3. A measurement that **exceeds** the relevant vendor ceiling indicates a
   broken harness (e.g. errors counted as success, retries inflating counts)
   — investigate before publishing the number.
4. Once measured, add a `RESULTS.md` next to this file with date, git SHA,
   environment, and k6 summary output. Do not edit this file's ceilings to
   match measurements; ceilings stay vendor-claimed.
